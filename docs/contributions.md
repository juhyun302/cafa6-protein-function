# 개인 기여 | 이주현

**담당 범위:** AlphaFold DB 구조 수집 → Foldseek 검색 → GO 기능 전이·상향 전파 → 팀 예측과의 앙상블.

단백질의 기능을 직접 학습하는 새 구조 모델을 만드는 대신, 공개 구조와 알려진 기능 정보를 검색·전이하는 branch를 구현했습니다. 이 문서는 당시 해결한 문제와 현재 정리된 코드를 연결합니다.

Kaggle 92위·은메달은 팀 공동 성과입니다. 홍지승 작성 서열 모델은 [별도 보존 폴더](../models/sequence_baselines/README.md)에서 구분합니다.

## 1. 단백질 ID와 구조 수집 흐름 구성

**문제:** FASTA의 ID, AlphaFold 구조 파일명, 참조 annotation의 ID가 맞아야 검색 결과를 기능 정보로 연결할 수 있습니다. 반복 실행 때 같은 구조를 계속 받거나 불완전한 파일을 재사용하는 문제도 고려해야 했습니다.

**당시 구현:** accession 추출·중복 제거, AlphaFold DB API를 통한 CIF 다운로드, 기존 구조 파일 검사와 재사용, 성공·미확보 목록 기록을 구현했습니다. 스레드·비동기 다운로드 버전과 소규모 점검 코드를 실험했습니다.

**현재 확인할 코드:** [download.py](../src/cafa_pipeline/download.py), [io.py](../src/cafa_pipeline/io.py), [structure.py](../src/cafa_pipeline/structure.py)의 extract_accessions.

현재의 명시적인 실패 상태·일부 예외 처리와 통합 CLI는 후속 정리에서 보완한 내용입니다. 기존 AlphaFold DB 구조를 수집한 것이며 AlphaFold 모델을 새로 학습하거나 구조를 직접 생성한 작업은 아닙니다.

## 2. Azure ML 배치 검색과 결과 병합

**문제:** 많은 구조 파일을 한 번에 비교하는 검색 흐름과, 여러 배치의 결과를 후속 GO 처리에 연결하는 작업이 필요했습니다.

**선택과 구현:** Foldseek로 참조 DB와 배치 query DB를 만들고, Azure ML CPU 환경에서 검색·7열 TSV 변환·결과 병합을 수행하는 흐름을 구성했습니다. 원래 검색 코드의 batch_size는 5,000, max-seqs는 20입니다. 발표에서는 32코어 CPU 환경을 소개했습니다.

**보존된 결과:** 당시 노트북 실행 출력에 배치 파일 **30개**, 병합 결과 **2,488,745행**이 남아 있습니다. 이는 검색 hit 행 수이며 단백질 수와 다릅니다. 원본 전체 TSV를 다시 생성해 재계산한 결과는 아닙니다.

**현재 확인할 코드:** [search.py](../src/cafa_pipeline/search.py), [structure.py](../src/cafa_pipeline/structure.py)의 merge_hits, [Azure 제출 안내](../azureml/README.md).

실행 시간·사용 비용의 완전한 원본 기록이 없어 처리 속도나 비용 절감 배수는 제시하지 않습니다. [저장된 출력 근거](evidence/README.md)

## 3. 구조 hit에서 GO 기능 점수 생성

**문제:** 구조 검색 결과는 유사한 단백질 목록이므로, 이를 GO 기능별 예측 점수로 변환해야 했습니다. 구조 hit가 있어도 대상 단백질의 기능 annotation이 없으면 전이가 되지 않습니다.

**구현:** query·target ID를 참조 annotation과 맞추고 self-hit를 제외한 뒤, alntmscore를 가중치로 GO별 점수를 누적하는 처리를 구현했습니다. 단백질별 최대 GO 점수로 정규화하고 후보를 선별했습니다.

**문제 해결 관점:** 구조 확보, 검색 hit, annotation 연결, GO 전이 성공을 서로 다른 단계로 살펴보았습니다. 과거 회고에는 초기 100개 실험에서 이 단계들의 누락 원인을 구분한 기록이 있습니다. 세부 표본과 수치의 출처는 [프로젝트 경과](project-history.md)에 분리했습니다.

**현재 확인할 코드:** [structure.py](../src/cafa_pipeline/structure.py)의 transfer_go·normalize_scores.

합산 점수와 정규화한 상대 점수를 정답 확률로 설명하지 않습니다. 당시 ID 정리 셀과 현재의 공통 ID 정리 함수는 구현 형태가 다릅니다.

## 4. GO 계층 일관성과 후보 수 관리

**문제:** 세부 기능의 점수가 상위 기능보다 높아지는 불일치와, 조상 term 추가 후 후보 행이 증가하는 문제를 다뤄야 했습니다.

**구현:** GO 조상 행렬을 이용해 자식 점수를 부모·조상으로 max 전파하고, namespace별 결과와 Top-N 제출 후보를 생성했습니다. 예측 단백질 수와 GO 행 수를 나누어 결과를 확인했습니다.

초기 회고에는 Top-300·500·1000 후보 제한을 비교한 기록이 있습니다. 현재 설정의 전처리 Top-50과 namespace별 최종 Top-500은 서로 다른 단계입니다.

**현재 확인할 코드:** [structure.py](../src/cafa_pipeline/structure.py)의 load_ancestors·propagate·make_submission, [알고리즘 설명](structure-method.md).

새 코드의 작은 부모 TSV 지원·순환 검사·회귀 테스트는 후속 재현성 개선에 포함됩니다.

## 5. 구조 예측을 팀의 다른 예측과 결합

**문제:** 구조 branch가 모든 단백질과 기능을 포괄하지 않으므로, 팀의 다른 예측 결과를 보완하는 방식으로 활용해야 했습니다.

**구현:** 일정 점수 이상인 구조 예측을 기본 예측에 덮어쓰거나 추가하는 패치를 만들고, 다른 예측과 전체 행의 백분위 순위를 평균해 결합했습니다. 원래 앙상블 파일에는 InterPro 예측을 기본 입력으로 쓰는 기록이 있습니다.

**현재 확인할 코드:** [ensemble.py](../src/cafa_pipeline/ensemble.py)의 patch_scores·rank_ensemble.

0.99는 점수 임계값이며 통계적 신뢰구간이 아닙니다. 실제 코드는 BP 전용 필터나 단백질별 순위 평균이 아닌 전역 순위 평균입니다. 구조 branch만의 점수 개선 폭이나 최적 임계값을 확정할 전후 평가 원본은 현재 보존되어 있지 않습니다.
